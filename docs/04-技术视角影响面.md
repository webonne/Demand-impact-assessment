# 04 · 技术视角影响面（接口 / 模块）

## 定位：不是第二套分析，是同一影响面的技术剖面

业务视角回答「关联哪些系统功能」，技术视角回答「哪些接口、哪些模块被影响」。
两者不是并列的两次分析 —— 技术视角是**业务影响面在接口/模块层的投影**，
外加一件业务视角做不到的事：**把依赖影响收窄到真正被波及的调用方**。

系统级 `depends_on` 有个天然粗糙点：前端几乎依赖所有服务，于是每份报告的
依赖影响里都有它，看多了就会被忽略。接口级依赖让结论从「商城前端（整个）」
精确到「商城前端·结算页模块，因为它调用了需改动的订单试算接口」——
同时把没调用受影响接口的调用方**排除**出影响面。技术视角的价值在「更准」，
不在「更多」。

## 数据结构：interfaces.yaml（可选文件）

接口/模块层维护在 `data/panorama/interfaces.yaml`，与 domains.yaml 解耦：
业务文件不感知接口，业务/技术两个文件可以各自演进、由不同角色维护。

```yaml
modules:
  - id: mod-order-pricing
    name: 计价模块
    system: svc-order                 # → 系统
    path: order-service/pricing/      # 代码目录（可选）

interfaces:
  - id: if-order-price
    name: 订单试算
    kind: http                        # http | rpc | mq | job
    system: svc-order                 # 接口归属系统
    ref: "POST /api/order/price"      # 契约标识：路径 / RPC 方法 / topic 名
    module: mod-order-pricing         # → 实现模块（可选）
    exposed_by: [fp-order-price]      # → 功能点（业务→技术的映射边）
    called_by: [mod-h5-checkout]      # → 调用方：系统或模块 id
```

### 新增的边类型

| 边 | 方向 | 影响面上的含义 |
| --- | --- | --- |
| `exposes` | 功能点 → 接口 | 改功能点 = 动这些契约（由 `exposed_by` 反向生成） |
| `calls` | 系统/模块 → 接口 | 接口级调用，细化 `depends_on`（由 `called_by` 反向生成） |
| `implemented_in` | 接口 → 模块 | 定位到「改哪个模块」 |

`called_by` 支持模块 id：把调用方精确到「商城前端·结算页模块」，
依赖影响的结论粒度随之变细。

## 投影与收窄规则（全确定性，不引入 LLM）

1. **接口投影**：受影响功能点沿 `exposes` 投影到接口 ——
   direct 层功能点的接口标 **需改动**（开发任务），
   process/data 层功能点的接口标 **回归验证**（测试任务）；
   同一接口两种结论并存时「需改动」优先。
2. **模块定位**：受影响接口沿 `implemented_in` 落到模块；
   调用了需改动接口的调用方模块，标「回归验证」（需适配）。
3. **依赖收窄**：对每个受影响系统，调用方若声明了对它的接口级 `calls`：
   - 调用了需改动接口 → 计入依赖影响，理由精确到接口；
   - 没调用任何需改动接口 → **排除**，报告的「依赖收窄」块中留痕，供人工复核；
   - 一条 `calls` 都没声明 → 降级回系统级判断（与未引入技术视角时行为一致）。

### 两条安全阀

- **部分映射不收窄**：某系统的直接命中功能点里只要有一个没配 `exposed_by`，
  该系统的接口信息视为不完整，对它的依赖判断整体降级回系统级。
  宁可结论粗一点，不能因为图谱没补全而漏报。
- **排除必须留痕**：被收窄排除的调用方在报告中显式列出（而非静默消失），
  接口图谱有遗漏时评估人能一眼发现。

## 建议规则（技术视角新增）

| 触发条件 | 建议 |
| --- | --- |
| 需改动接口的调用方属于其他团队 | 接口评审对齐 + 契约测试（contract test） |
| 需改动接口中有 MQ 消息 | 消息体兼容性评估（新旧消费者共存期只增不改不删字段） |
| 疑似新功能点（故事未匹配） | 预计需新增接口，回补全景图时连功能点带接口一并登记 |

## 校验规则（req-insight validate）

- 引用完整性：接口的 system/module/exposed_by/called_by、模块的 system 必须存在；
  `kind` 必须是 http/rpc/mq/job。
- **两级依赖一致性**：http/rpc 接口的调用方系统必须声明 `depends_on` 接口归属系统，
  否则告警（mq/job 是异步消费，不要求）。这个软校验能反向发现 `depends_on` 漏配。
- 没有关联任何功能点的接口给出告警 —— 技术视角无法投影到它。

## 维护路线：手工起步，导入为目标

接口数量通常是功能点的数倍，全量手工维护会腐烂。落地路线：

1. **起步（现在）**：只给高频改动域补接口 —— 示例仓库刻意只覆盖了
   交易域 + 积分服务，其余域演示降级行为。缺失部分行为与旧版完全一致，
   所以可以按域渐进推进，没有「先梳理完才能用」的门槛。
2. **生长**：与功能点一样走「疑似新功能点 → 回补」闭环，
   新需求评审时连功能点带接口一起登记；改图走 PR，由接口归属团队评审。
3. **目标态**：接口清单从 OpenAPI / proto / 服务注册中心定期同步生成，
   人只维护 `exposed_by`（功能点 ↔ 接口）这一层映射（见 Roadmap）。

## 常用命令

```bash
req-insight validate     # 含接口/模块层校验（引用完整性 + 两级依赖一致性）
req-insight run ...      # 报告第 4 节自动包含「技术影响面（接口/模块）」
```
