# 01 · 业务全景图与知识图谱

## 为什么要重新梳理

影响面评估的前提，是有一张「需求可以落进去」的地图。这张地图要满足三点：

1. **粒度到功能点**：域/系统粒度太粗，评估不出「改哪里」；代码粒度太细，业务方看不懂。
   功能点（如「订单计价」「退款执行」）是业务与研发都能对话的最小单元。
2. **不只是树，还是图**：域 → 能力 → 功能点是树状目录，但影响是沿「关系」传播的 ——
   功能点由哪个系统实现、读写哪些数据、触发哪个下游流程、系统之间谁调用谁。
   这些关系构成知识图谱，影响面分析就是在图上做有界遍历。
3. **可维护**：地图会过时。所以用「图谱即代码」——YAML 放在仓库里，改图走 PR 评审，
   CI 里跑 `req-insight validate` 保证引用完整。

## 数据结构

两个 YAML 文件（`data/panorama/`）：

### domains.yaml —— 业务结构（树）+ 功能点关系（图）

```yaml
domains:
  - id: dom-trade          # 业务域
    name: 交易域
    capabilities:
      - id: cap-order      # 业务能力
        name: 下单
        function_points:
          - id: fp-order-price       # 功能点：需求落点、影响面最小单元
            name: 订单计价
            description: 订单金额计算：商品价、运费、优惠分摊
            keywords: [计价, 金额, 价格, 优惠, 抵扣, 分摊, 运费]   # 匹配用
            implemented_by: [svc-order]   # → 系统
            reads: [ent-coupon]           # → 读数据实体
            writes: [ent-order]           # → 写数据实体
            triggers: [fp-pay-create]     # → 业务流程下游功能点
            criticality: high             # 关键度，high 触发风险提示
```

### systems.yaml —— 系统与数据实体

```yaml
systems:
  - id: svc-order
    name: 订单服务
    owner: 交易组                 # 报告里汇总「涉及团队」
    depends_on: [svc-user, svc-promo]   # A depends_on B = A 调用 B

entities:
  - id: ent-order
    name: 订单
    owned_by: svc-order
```

### interfaces.yaml —— 接口/模块层（可选，技术视角）

接口、模块，以及 功能点 ↔ 接口、调用方 → 接口 的映射。缺失时技术视角
自动降级为系统级结论。详见 [04-技术视角影响面.md](04-技术视角影响面.md)。

### 图谱中的边类型

| 边 | 方向 | 影响面上的含义 |
| --- | --- | --- |
| `contains` | 域 → 能力 → 功能点 | 结构归属（渲染用，不参与传播） |
| `implemented_by` | 功能点 → 系统 | 改功能点 = 改这个系统 |
| `triggers` | 功能点 → 功能点 | 业务流程下游，改上游要冒烟下游 |
| `writes` / `reads` | 功能点 → 数据实体 | 写方变更影响同一实体的其他读方 |
| `depends_on` | 系统 → 系统 | 被依赖方行为变化，波及上游调用方 |
| `exposes` | 功能点 → 接口 | 改功能点 = 动这些契约（技术视角） |
| `calls` | 系统/模块 → 接口 | 接口级调用，细化 `depends_on`（技术视角） |
| `implemented_in` | 接口 → 模块 | 定位到改哪个模块（技术视角） |

## 维护流程

1. **初次梳理**：按域 → 能力 → 功能点自顶向下盘点。功能点不求一步到位，
   先覆盖高频改动的域；`keywords` 写足（同义词、业务黑话都放进去），命中率才高。
2. **随需求生长**：影响评估报告会标出「疑似新功能点」（没匹配到任何功能点的故事）。
   评审确认后，把新功能点补进 YAML —— 全景图靠每个需求持续校准，而不是一年一次大梳理。
3. **改图走 PR**：`keywords`、`triggers`、`depends_on` 的变更都影响后续所有需求的评估结论，
   由对应域的 owner 评审。
4. **CI 校验**：`req-insight validate` 检查 ID 唯一性、引用完整性，
   并对缺 keywords / 缺 owner / 缺实现系统的节点给出警告。

## 常用命令

```bash
req-insight validate                 # 校验
req-insight panorama -o 全景图.md    # 渲染 mermaid 总览（域/能力/功能点 + 跨域触发链路）
```
