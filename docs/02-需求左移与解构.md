# 02 · 需求左移与解构

## 为什么往左移

影响面评估如果直接拿原始需求全文去匹配功能点，噪声很大：需求文档里有背景、
有竞品分析、有废话。先把需求**解构**成结构化产物，再拿结构化产物去匹配，
一石二鸟：

- **评估影响面**：用户故事自带 keywords，匹配功能点更准；
- **帮助开发理解需求**：旅程、故事、泳道图本来就是研发开卡前最想要的资料。

## 原始需求的两种形态

`intake` 模块把不同输入归一化为 `RawRequirement`（markdown + YAML front matter）：

| source_type | 输入 | 解构策略 |
| --- | --- | --- |
| `document` | 常规需求文档 | 忠实解构；含糊处记 open_questions |
| `demo` | **没有文档，直接给一个 demo**：输入是 demo 走查记录（页面、交互、状态、字段） | 先逆向还原（枚举界面/交互/状态 → 反推任务与业务规则），demo 未覆盖的分支/异常一律进 open_questions，推断进 assumptions |

```markdown
---
id: REQ-2026-002
title: 售后进度可视化
type: demo        # 不写则按文件名含 "demo" 自动识别
---
（正文：文档内容 或 demo 走查记录）
```

> demo 型需求最大的坑是「把 demo 当成完整需求」。demo 只演示了 happy path，
> 解构提示词强制模型把未覆盖部分显式列为待澄清问题，而不是脑补。

## 解构产物（Artifacts）

统一 YAML 存档（示例：`examples/artifacts/REQ-2026-001.artifacts.yaml`）：

| 字段 | 用途 |
| --- | --- |
| `summary` | 需求一句话概述，进报告第一节 |
| `journeys` | 用户旅程：阶段 × (用户动作 / 触点 / 系统行为 / 备注)，渲染成 mermaid journey + 表格 |
| `stories` | 用户故事：作为…我希望…以便… + 验收标准 + **keywords（影响面匹配的输入）** |
| `swimlane_mermaid` | 泳道图（mermaid sequenceDiagram），参与方对齐全景图中的系统 |
| `glossary` | 术语表 |
| `assumptions` | 解构时做出的推断，需评审确认 |
| `open_questions` | 待澄清问题，评审会上逐条过 |

## 两种工作模式

### LLM 模式

```bash
req-insight decompose examples/raw/REQ-2026-001-积分抵扣.md -o REQ-2026-001.artifacts.yaml
# 或端到端：
req-insight run examples/raw/REQ-2026-001-积分抵扣.md -o report.md
```

- 默认模型 `claude-opus-4-8`，结构化输出（JSON Schema）保证产物可解析；
- 提示词会**注入业务全景图摘要**（域/能力/功能点/关键词），要求故事 keywords
  优先复用全景图用语 —— 这是解构与匹配两个环节的关键衔接；
- 需要 `pip install 'req-insight[llm]'` 并配置 `ANTHROPIC_API_KEY`（或 `ant auth login`）。

### 离线模式（无 API Key / 人工把关）

```bash
req-insight decompose xxx.md --print-prompt   # 打印提示词
# → 贴给任意模型，或 BA 直接人工编写 artifacts YAML
req-insight run xxx.md --artifacts xxx.artifacts.yaml -o report.md
```

产物 YAML 是普通文件，人工修订后重跑 `impact` 即可 —— LLM 产出只是初稿，
**评审后的 artifacts 才是需求资产**，建议随需求归档进仓库。
