# 03 · 影响面分析与建议

## 第一步：用户故事 → 功能点匹配

匹配是确定性的关键词打分（`matching/mapper.py`），可解释、零依赖：

| 信号 | 分值 |
| --- | --- |
| 功能点名称出现在故事文本中 | +3 |
| 功能点 keyword 命中 | 每个 +1 |
| 所属能力名称命中 | +0.5（弱信号） |

- 故事文本 = 标题 + 作为/我希望/以便 + 验收标准 + keywords；
- 每个故事取 Top-3、分数 ≥ 1.0 的候选；报告中列出**匹配依据**（命中了哪些词），
  评估人可以肉眼复核；
- **未匹配的故事 = 疑似新功能点**：报告显式标出，提示补充全景图。
  这是全景图持续生长的入口，不是匹配失败的垃圾桶。

> 关键词匹配的准确率取决于全景图 keywords 的维护质量。Roadmap 中计划引入
> LLM 复核 / 向量召回作为兜底，但确定性匹配始终保留 —— 影响面结论必须可解释。

## 第二步：知识图谱影响传播

从命中的功能点出发，沿图做有界遍历（`graph/impact.py`），分四层：

| 层级 | 传播规则 | 回答的问题 |
| --- | --- | --- |
| **direct 直接影响** | 命中功能点 + `implemented_by` 系统 | 这个需求要改什么 |
| **process 流程影响** | 沿 `triggers` 边向下游传播（默认 ≤3 跳） | 改了它，业务链路下游谁会被牵动 |
| **data 数据影响** | 直接功能点 `writes` 的实体 → 该实体的其他 `reads` 方 | 数据口径变了，谁在消费这份数据 |
| **dependency 依赖影响** | 反查 `depends_on`：谁调用了受影响系统 | 接口/行为变化会波及哪些上游 |

设计取舍：

- **传播有界**：triggers 限深度、数据影响只做一跳（写方 → 读方），避免「全图都受影响」
  的无效结论；影响面报告要的是「值得看一眼的范围」，不是可达性闭包。
- **层级有优先级**：同一节点命中多层时，direct 优先；图渲染取最高层级着色，
  表格保留各层原因（一个功能点既是流程下游又是数据读方，两个原因都值得知道）。

## 第三步：建议生成

规则化生成（`_build_suggestions`），当前包括：

1. **回归测试范围**：全部受影响功能点清单；
2. **跨团队协作**：受影响系统的 owner 团队 ≥2 时，提示评审拉通、对齐排期与接口契约；
3. **高关键度风险**：`criticality: high` 的功能点进入影响面时，建议灰度/开关/监控；
4. **数据变更**：涉及实体写入变化时，提示存量兼容、报表口径、数据订正；
5. **流程下游冒烟**：process 层功能点建议至少做冒烟验证。

规则集刻意保持简单 —— 建议的价值在「别漏了」，不在「多聪明」。新规则按需加。

## 报告结构

`req-insight impact / run` 输出 markdown 报告：

1. 需求概要
2. 用户旅程（mermaid journey + 表格）
3. 用户故事 → 功能点映射（含未匹配标注）
4. 影响面分析（影响图 mermaid + 四层表格 + 涉及团队）
5. 泳道图
6. 建议
7. 附：术语表 / 假设 / 待澄清问题（checkbox，评审会逐条过）
